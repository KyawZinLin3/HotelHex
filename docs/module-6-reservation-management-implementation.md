# Module 6 Reservation Management implementation

The Module 6 FRD defines an extensive reservation capability. This implementation delivers the P0 single-room booking workflow in the existing HotelHex Next.js/NestJS/Prisma application. The reservation screen is available at `/reservations`, linked from the main navigation. The API is rooted at `/api/v1/reservations`.

## Delivered P0 behavior

- Scoped property and branch selection; hotel-group ownership is derived on the server from the authorized property.
- Overnight, hourly, and day-use availability searches using the property time zone, occupancy limits, stay policy, active inventory, existing reservations, unreleased room holds, and turnover buffers for hourly/day-use stays.
- Rate-plan quote lookup through the existing Rate Management service. Reservation writes recheck availability inside a serializable transaction and allocate a property/branch/year booking number.
- Single-room tentative reservation creation from an active guest, with guest/contact and cancellation/deposit-policy snapshots, itemized price snapshots, source/segment/reference, notes and special requests.
- Duplicate overlapping-stay warning with an explicit reason override; versioned updates, explicit repricing, confirm/cancel/no-show actions, room assignment, and deposit/guarantee tracking.
- Request/note/history endpoints, paged reservation listing and basic status/source/stay-type reporting. Contact fields are masked according to existing guest contact permissions.
- Reservation permission catalog registration at API startup. Existing user permissions are not silently expanded.

## FRD review resolutions

- The high-level scope list names multi-room reservations as in scope, while the explicit P0/P1 breakdown places multi-room and group reservations in P1. The implementation follows the explicit MVP breakdown and keeps P0 at one room per reservation.
- The FRD says tentative inventory consumption is configurable. The current implementation conservatively counts `TENTATIVE`, `PENDING_GUARANTEE`, and `CONFIRMED` reservations as consuming inventory; the setting to vary this is not implemented.
- The FRD expects expired tentative reservations to release inventory. The `EXPIRED` state is modeled, but there is no expiry worker, so tentative inventory remains consuming until an authorized user changes its state.
- Availability uses property-local date/time conversion and rate snapshots. Existing rate quotes currently return zero tax and service charge, and cancellation policy evaluation / billing posting are not available in the existing modules; these are called out as integration work instead of inferred behavior.
## API surface

`GET /properties`, `GET /options`, `POST /availability/search`, `GET /`, `POST /`, `GET /:id`, `PUT /:id`, `POST /:id/{confirm,cancel,no-show,reprice,room}`, `PUT /:id/guarantee`, `GET|POST /:id/{requests,notes}`, `GET /:id/history`, `GET /reports`, and `POST /catalog`.

All authenticated routes use the existing bearer token. Property and branch selectors are query parameters for scoped routes; availability also accepts them in its JSON body. Reservation edits and state changes require the current integer `version`. Availability search and reservation creation require a selected property and accessible branch.

## Setup and permissions

The additive SQL migration is [reservation-management.sql](../prisma/reservation-management.sql). It was generated by diffing the current local PostgreSQL schema against `prisma/schema.prisma` and applied to the configured local database. For another installation, back up the database, review the SQL, then apply it once with Prisma's `db execute --file prisma/reservation-management.sql --schema prisma/schema.prisma` command. Regenerate the Prisma client with `npm run db:generate` after schema changes.

Assign the reservation permissions required by each role in Security. Typical reservation staff need `RESERVATION.BOOKING.VIEW`, `RESERVATION.BOOKING.CREATE`, `RESERVATION.RATE.VIEW`, and `RESERVATION.REPORT.VIEW`, plus relevant workflow actions. Physical-room assignment also requires existing `ROOM.VIEW`. The existing Rate service also enforces `RATE.PLAN.VIEW` and `RATE.PRICE.VIEW`; creating or searching quotes therefore needs both the reservation rate permission and existing Rate Management permissions. Guest selection requires existing `GUEST.PROFILE.VIEW`. Full contact reveal remains controlled by `GUEST.CONTACT.VIEW` / `GUEST.CONTACT.VIEW_FULL`; the reservation options endpoint intentionally returns guest names and IDs only.

Run the portal with the normal repository workflow. `npm run build` builds both the Next.js portal and NestJS API. The route follows the existing configured API URL (`NEXT_PUBLIC_API_URL`, defaulting to `http://localhost:4000/api`).

## Scope and known integration limits

- **P0 single room only:** one reservation consumes one room of one room type. Multi-room reservations, split/linked bookings, group blocks, shared rooming lists and multi-property search are deferred to the FRD's P1 work.
- **Front Desk handoff only:** no check-in/check-out, room moves during an active stay, folio or billing integration is claimed. The reservation status is prepared for a later Front Desk module.
- **Payment processing is not implemented:** guarantee/deposit values are tracked as reservation records; this does not charge a payment instrument, reconcile a gateway, or post a folio payment.
- **Cancellation assessment is review-only:** cancellation stores the policy snapshot and marks the outcome for staff review. It does not calculate/post a penalty because billing and the detailed policy evaluator are not integrated.
- **Rate limitations:** the current Rate Management quote returns zero service charge and tax. Reservations preserve the quote faithfully; no tax, fee, or payment behavior is invented here.
- **Tentative expiration:** tentative inventory remains consuming until staff changes its state; no expiry scheduler or automatic hold-release workflow is present.
- **Availability/assignment limits:** inventory counts eligible physical rooms by type and blocks all unreleased room holds. A physical room can be assigned only when clean/inspected and conflict-free; reservations do not automatically change housekeeping status.
- **Configuration/reporting:** source and segment additions are available. Basic aggregate reports are implemented; configurable booking rules, date-range reports, forecast analytics, exports, waitlists, calendars, and channel-manager sync are deferred.
- **Performance and concurrency:** writes use serializable transactions and retry Prisma serialization conflicts. Hotel-scale load targets and concurrency behavior have not been benchmarked against production-like data.
